## 1. Executive Summary & Verdict

This adversarial audit evaluated the completed Phase 1 independent reference oracle implementation in `tfib_experiments/phase11_oracle/`. The prior Phase 1 validation report asserted complete oracle isolation, exact NIST FIPS 203 KAT reproduction, and verified implicit rejection behavior.

### High-Level Verdict: **CONDITIONALLY READY FOR INTEGRATION**
- **Binary and Linkage Isolation:** **Verified.** The built library `libindependent_oracle.a` and test runner `test_independent_oracle` import zero symbols from the workspace's production objects (`bin/obj/mlkem768_inst.o`, `algorithms/source_ref/`, or internal TFIB tables). Dynamic linkage is strictly confined to external `liboqs.9.dylib` and `libSystem.B.dylib`.
- **FIPS 202 SHAKE-256 Engine:** **Verified.** Tested across 13 adversarial boundary and stress cases against Python 3 `hashlib.shake_256` (spanning empty input, below/at/above the 136-byte block rate, multi-block absorbing, and multi-block squeezing up to 4096-byte input / 2048-byte output). Zero discrepancies observed.
- **Canonical Implicit Rejection:** **Verified.** Validated across multiple bit-flip mutations at 7 distinct ciphertext offsets ($0, 100, 384, 544, 960, 1000, 1087$). Every mutated ciphertext decapsulated to an exact byte-for-byte match with $J(z \mathbin{\Vert} c) = \text{SHAKE-256}(z \mathbin{\Vert} c, 32)$ and diverged from $K_{\text{valid}}$.
- **KAT Data Provenance:** **Partially verified.** The header `references/test_vectors/mlkem_expected_kat.h` was generated by `mlkem-native` (commit `fc269bc2d106`) via `scripts/autogen` with pseudorandom stream `notrandombytes`. While `liboqs` independently matches these vectors from seeds $(d, z, m)$, the vectors originate from the same upstream codebase as the in-tree production source.
- **Negative & Boundary Test Semantics:** **Partially verified.** Case 5a (SS tampering) only tests a local buffer `memcmp` without exercising oracle logic. Test 6 (all-zeros / all-ones CT) asserted `memcmp(ss, ss_kat_valid) != 0` rather than asserting equality with the expected rejection key $J(z \mathbin{\Vert} c)$, resulting in an inferred rather than direct assertion of rejection.
- **Automation & Failure Handling:** **Verified.** Clean-build automation works reliably. Intentional fault injection into the test runner proved that exit codes strictly propagate failure ($1$) and generate valid `"status": "FAIL"` JSON records.

## 2. Check 1: Source & Implementation Inspection

### 2.1 File Inventory
The oracle implementation consists of:

### 2.2 Expected-Value Sources and Independence
Inspection of `test_independent_oracle.c` line 11:
```c
#define MLK_CONFIG_PARAMETER_SET 768
#include "references/test_vectors/mlkem_expected_kat.h"
```
Header banner in `references/test_vectors/mlkem_expected_kat.h`:
```c
/*
 * Copyright (c) The mlkem-native project authors
 * WARNING: This file is auto-generated from scripts/autogen
 *          in the mlkem-native repository.
 * Generated with:
 *   d, z: consecutive 32-byte draws from a fresh notrandombytes stream
 *   m:    first 32-byte draw from a second, fresh notrandombytes stream
 */
```
**Observation vs. Inferred:**
- *Observed:* The file provides concrete 32-byte seeds: $d$ (`934d60b3...`), $z$ (`3e2a2ea6...`), $m$ (`934d60b3...`), and precomputed expected arrays for `pk`, `sk`, `ct`, `ss`.
- *Finding:* The test vector source is not an official NIST CAVP / ACVP submission file directly downloaded from NIST CSRC, but is the regression vector generated by `mlkem-native` (commit `fc269bc2d106`).
- *Assessment:* Because `algorithms/source_ref/mlkem` is also derived from `mlkem-native`, testing the in-tree production code against this header is not strictly external. However, `liboqs` is an independent implementation (using PQClean / Kyber C reference algorithms). When `liboqs` is fed $(d, z)$ and $m$, it produces the exact same `pk`, `sk`, `ct`, and `ss` byte-for-byte. Thus, the oracle independently validates that both implementations conform to the FIPS 203 mathematical specification for these seeds.
- **Classification:** **Partially verified** (Mathematical specification confirmed; vector source is upstream `mlkem-native` regression suite).

## 5. Check 4: Implicit Rejection Behavior & API Observability

### 5.1 Multi-Position Ciphertext Mutation Experiment
An adversarial test was constructed to systematically mutate ciphertext bytes across structural boundaries in ML-KEM-768 ciphertext $c = (c_1, c_2) \in \mathbb{Z}_q^{3 \times 256} \times \mathbb{Z}_q^{256}$ (total length 1088 bytes: $c_1$ = 960 bytes, $c_2$ = 128 bytes):

```text
VERDICT: ALL_MUTATIONS_PROVED_REJECTION_PASS
```

### 5.2 API Observability Analysis
- **Observed Behavior:**
  - `OQS_KEM_ml_kem_768_decaps(ss, ct_mutated, sk)` returned return code `0` (`OQS_SUCCESS`) for all mutated ciphertexts.
  - The returned 32-byte shared secret `ss` matched the independent calculation $\text{SHAKE-256}(z \mathbin{\Vert} c_{\text{mutated}}, 32)$ with 0 byte differences across all offsets.
  - The returned shared secret differed completely from $K_{\text{valid}}$ across all 32 bytes.
- **Why Return Code is 0:** Under FIPS 203 §7.3 (Algorithm 17), ML-KEM is explicitly defined as an *implicitly rejecting* KEM. It does not abort or signal errors to the caller on invalid ciphertexts in order to prevent chosen-ciphertext side-channel timing attacks. Therefore, `OQS_SUCCESS` is the expected, standard-compliant API return code.
- **How Rejection is Established Indirectly:** Because $z = sk[2368..2399]$ is a 256-bit uniform random secret, the output of $\text{SHAKE-256}(z \mathbin{\Vert} c, 32)$ is unpredictable and pseudorandom. The probability of an authentic decapsulation path producing this exact 32-byte value is bounded by $2^{-256}$. Observing an exact 32-byte match with $J(z \mathbin{\Vert} c)$ proves conclusively that the implementation took the implicit rejection branch.
- **What Remains Unobservable:** The internal intermediate message $m'$, the re-encrypted ciphertext $c'$, and the internal constant-time conditional multiplexer are internal to `liboqs` and unobservable via the public C interface.
- **Classification:** **Verified.**

## 6. Check 5: KAT and Negative-Test Semantics Audit

### 6.1 Deterministic KeyGen, Encaps, and Decaps KATs
- **Test 1 (KeyGen):** Seed $d \mathbin{\Vert} z$ fed to `independent_oracle_keypair_derand` reproduced `test_vector_pk` (1184 bytes) and `test_vector_sk` (2400 bytes) with 0 differences. **Classification: Verified.**
- **Test 2 (Encaps):** Public key and seed $m$ fed to `independent_oracle_encaps_derand` reproduced `test_vector_ct` (1088 bytes) and `test_vector_ss` (32 bytes) with 0 differences. **Classification: Verified.**
- **Test 3 (Decaps):** Authentic ciphertext and secret key fed to `independent_oracle_decaps` reproduced `test_vector_ss` (32 bytes) with 0 differences. **Classification: Verified.**
- **Test 4 (Rejection):** Mutated ciphertext decapsulated to $J(z \mathbin{\Vert} c)$ with 0 differences. **Classification: Verified.**

### 6.2 Audit of Negative Tests & Identified Deficiencies

#### Defect 1: Test 5a is a Trivial Buffer Comparison (Severity: Low)
- **Code in `test_independent_oracle.c` lines 164-167:**
  ```c
  uint8_t ss_tampered[32];
  memcpy(ss_tampered, ss_enc_out, 32);
  ss_tampered[15] ^= 0x42;
  bool neg_ss_detected = (memcmp(ss_tampered, ss_enc_out, 32) != 0);
  ```
- **Audit Finding:** This test simply asserts that flipping a bit in a local stack array causes `memcmp` against the original array to return non-zero. It does not call any oracle function. It is a tautology that does not exercise the oracle.
- **Classification:** **Unsupported as an Oracle Correctness Check.**

#### Defect 2: Test 6 Asserts Output Inequality Rather than Implicit Rejection (Severity: Medium)
- **Code in `test_independent_oracle.c` lines 206-216:**
  ```c
  uint8_t ct_zeros[ORACLE_MLKEM768_CT_BYTES] = {0};
  uint8_t ss_zeros[32];
  independent_oracle_decaps(ss_zeros, ct_zeros, sk_out);
  bool zeros_rejected = (memcmp(ss_zeros, ss_enc_out, 32) != 0);
  ```
- **Audit Finding:** The test passes if `ss_zeros` does not equal `ss_enc_out`. However, `ss_enc_out` is the shared secret for `test_vector_ct`, a completely different ciphertext. Even if decapsulation produced a valid decrypted session key for an all-zeros ciphertext, that session key would naturally not equal `ss_enc_out`.
- **Adversarial Check:** When we computed the exact canonical rejection value $J(z \mathbin{\Vert} \mathbf{0})$ and $J(z \mathbin{\Vert} \mathbf{1})$, `ss_zeros` and `ss_ones` matched $J(z \mathbin{\Vert} c)$ bit-for-bit. Thus, the implementation *does* reject all-zeros and all-ones ciphertexts, but the test assertion `memcmp(ss_zeros, ss_enc_out, 32) != 0` was an imprecise proxy rather than a direct verification.
- **Classification:** **Partially verified** (Behavior factually occurs in the library, but test assertion is weak).
